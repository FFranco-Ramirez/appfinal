1. Requisitos Funcionales

1.1 Gestión de Sensores (alta y asociación)

“Desde la aplicación móvil se debe permitir agregar nuevos sensores RFID (tarjetas o llaveros) asociados a un departamento y a un usuario administrador:
o La app debe disponer de una pantalla de ‘Gestión de Sensores’. El administrador debe poder ingresar: Código único del sensor (MAC / UID RFID). Estado inicial del sensor (activo, inactivo, perdido, bloqueado). Al guardar, la app debe: Enviar la información a la API en AWS. Registrar el sensor en la tabla correspondiente (por ejemplo: sensores). Asociar el sensor al departamento y al usuario.”
— funcionesDeApp.txt
  • Pantalla de Gestión de Sensores (solo admin).
  • Alta de sensor con campos: UID/MAC, estado inicial, tipo (llavero/tarjeta), apodo opcional.
  • Asociación a departamento y usuario administrador.
  • Envío a API AWS para registro en BD.

1.2 Activar / Desactivar / Bloquear / Marcar como Perdido

“La aplicación móvil debe permitir cambiar el estado de cada sensor (ej.: activo / inactivo) desde la pantalla de gestión. Solo el usuario administrador del departamento puede: Activar o desactivar un sensor, marcar un sensor como ‘perdido/bloqueado’. El cambio debe reflejarse de inmediato en la BD en AWS para que el NodeMCU considere el nuevo estado en la validación de acceso.”
— funcionesDeApp.txt
  • Cambio de estado de sensor desde la app (admin únicamente).
  • Estados soportados: activo, inactivo, perdido, bloqueado.
  • Reflejo inmediato en BD para que el microcontrolador valide según estado.

1.3 Control Manual de Barrera

“Abrir (levantar) la barrera manualmente mediante un botón ‘Abrir barrera’. Cerrar (bajar) la barrera manualmente mediante un botón ‘Cerrar barrera’. La app debe: Enviar la acción al backend/API, que a su vez notifica al microcontrolador (NodeMCU). Mostrar el estado actual de la barrera (Abierta / Cerrada). Toda apertura/cierre manual debe registrarse como evento de acceso en la BD.”
— funcionesDeApp.txt y evaluacion.txt
  • Botones “Abrir barrera” y “Cerrar barrera”.
  • API encola comando; NodeMCU ejecuta; BD registra evento (APERTURA_MANUAL/CIERRE_MANUAL).
  • Visualización de estado actual de barrera.

1.4 Visualización de Historial y Estado en Tiempo Real

“Mostrar el estado en tiempo real de los accesos (Válido - Fallido). Identificar quién intenta ingresar y mostrar las opciones: Permitir Acceso… Denegar Acceso…”
— funcionesDeApp.txt
  • Listado de eventos de acceso (válido/denegado) con fecha/hora.
  • Identificación del usuario/sensor en el intento de acceso.
  • Opciones de permitir/denegar desde la app (manual, si aplica al flujo).

1.5 Roles y Usuarios

“Múltiples usuarios por departamento… Rol de administrador por departamento… Funciones exclusivas del administrador… Usuarios operadores… No pueden agregar, eliminar ni cambiar estados de sensores.”
— evaluacion.txt
  • Admin único por departamento; operadores no pueden gestionar sensores.
  • Administración de usuarios: agregar, modificar, eliminar (requerido en app).
  • Asociación de sensores y permisos por departamento.

1.6 Validación de Acceso (flujo del sistema IoT)

“Si el llavero o Tarjeta RFID es válido: aro LED verde, servo levanta barrera, baja a los 10 segundos, registrar fecha/hora, visualizar en app. Si no tiene acceso: aro LED rojo, registrar el evento, visualizar en app.”
— evaluacion.txt
  • Validación por NodeMCU contra BD (via API).
  • Accionamiento físico (LED/servo) y registro de evento.
  • Visualización inmediata del evento en la app.

5. Dependencias entre Requisitos

  • App “Gestión de Sensores” depende de API create.php, update_status.php y de un endpoint de listado (list.php).
  • App “Historial de Accesos” depende de endpoint de eventos (p. ej. access_events_list.php) y de que NodeMCU registre eventos (válido/denegado, apertura/cierre manual).
  • Control de Barrera en la app depende de control.php y de que NodeMCU consuma next_command.php.
  • Validación RFID depende de BD de sensores y de validate.php (NodeMCU).
  • Roles (admin único por departamento) dependen de diseño de BD y de lógica en API que lo haga cumplir.
